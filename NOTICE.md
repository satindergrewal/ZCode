# ZCode Feature Notes and Third-Party Component Notices

This notice applies to the source code published in this repository and its build artifacts. Each runtime form differs in features, permissions, storage locations, and network behavior; the default settings of one form must not be read as project-wide settings.

## 1. AI output, execution permissions, and automation risks

AI-generated code, commands, explanations, files, and suggestions may contain errors, omissions, security flaws, or third-party rights issues. Verify them against the actual files, command exit statuses, tool results, and tests; a model claiming something is "done", "handled safely", or "authorized" does not constitute fact or proof of authorization. Before important operations, review the execution targets, recipients, and impact, and keep recoverable backups.

Files, terminals, Git, Agent tools, and external processes can read and write files, start processes, and access the network within the permissions of the OS account that actually runs them. In Web or remote workspaces, operations may happen on the server, an SSH host, WSL, or inside a container; the device showing the current page does not tell you where execution happens. The current shared Agent execution adapter provides no default OS sandbox; the working directory, workspace identity, Git worktree, browser page isolation, and the Node REPL runtime context must not be treated as system-level isolation guarantees for all tools.

The shared runtime configuration defaults to the `build` permission mode; when the standalone CLI runs non-interactive tasks via `--prompt` without `--mode`, it uses `yolo`. Interactive sessions, desktop sessions, resumed tasks, and hosts may use their own configured, saved, or passed-in modes. Whether each step asks for confirmation depends on tool declarations, permission rules, and the run mode; `yolo` without read-only planning constraints enabled lets ordinary tool operations through, while interactive tools and tools that explicitly require confirmation keep their own rules. Model tool approval is not a global permission switch for the whole app; do not assume terminal operations, plugin processes, or update downloads go through the same approval flow. See [CLI prompt modes](apps/zcode-cli/packages/cli/src/run.ts#L486) and [tool permission decisions](apps/zcode-cli/packages/core/src/permission/service.ts#L97).

## 3. Local data, logs, and credentials

Data may be stored separately on desktop devices, in browsers, on the host running the CLI, in SSH/WSL environments, and in external services. The desktop and server data directories depend on the runtime environment and launch configuration and contain settings, sessions, attachments, caches, task history, plugins, and logs; the standalone CLI session database defaults to `~/.zcode/cli/db/db.sqlite`. Closing a window, signing out, uninstalling the client, or deleting one workspace must not be understood as having cleared all copies in other environments, separate data directories, backups, and external services.

Memory features differ in defaults and entry points: the standalone CLI enables memory by default, while desktop app settings default to off. When enabled, saved sessions may be analyzed, memories persisted, and reused in later tasks; the related extraction or consolidation can produce extra model requests. Automation plans, run records, and unfinished tasks also have their own persistence locations; restoring those records does not guarantee that previous external operations were undone or can be replayed in full.

Shared-Agent model input/output logs are written locally by default in development and production runs, except in the test environment. Logs may contain prompts, code, context, tool arguments, and model replies; request headers and some image/video data are redacted, but not all user text can be assumed redacted. Production defaults to rotation and trimming; explicitly enabling full retention changes that behavior. The desktop main process, Host, scheduler, Web service, and remote daemon also keep their own logs and crash records; a single log's size cap does not imply a project-wide retention period.

Credential storage mechanisms also differ: the CLI shared credentials file is encrypted, with a default key derivable from local environment information, and the reader also accepts plaintext records; desktop/Node service credentials likewise use local encrypted files with configurable or environment-derived keys, not the system keychain; Web OAuth credentials may be stored in localStorage. Model configuration, environment variables, plugin/MCP settings, SSH configuration, and remotely synced data may also contain valid credentials; do not treat these stores as system keychain, hardware-isolated, or "never leaves this machine" guarantees.

The embedded browser persists browsing data; explicitly importing cookies and localStorage from other browsers gives it the corresponding login states. Clearing the cache and clearing all site data are different operations, and browser history, downloaded files, page recordings, and model logs are not necessarily removed by the same cleanup entry. Do not put real keys or tokens into version-controlled files. Before copying logs, uploading feedback, sharing conversations, or backing up data directories, check the recipient scope to avoid committing real credentials, raw sessions, and private project content to public repositories or issue reports.
